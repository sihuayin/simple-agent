Token 预算管理：估算 · 阈值 · 自动压缩 · /compact

要回答的问题：这套上下文预算逻辑对不对——① 发送前用"估算"决定要不要压缩（CJK 按 1.5 字符/token、其余按 4 字符/token）；② 超过阈值（默认窗口的 80%）自动压缩；③ 用户消息含 /compact 时强制压缩；④ 压缩后估算回落、对话继续。

设计约定（要验证的）：估算用于发送前决策（API 的真实用量只有调用后才知道）；API 返回的 usage.prompt_tokens 作为事后校准——若实际用量也超阈值，下一轮照样压缩（应对估算偏小）。固定开销 = 分层系统提示词 + 工具 schema；每条消息另计少量格式开销。压缩策略默认滚动摘要（保留最近 N 轮原文，更早的历史压成摘要，需一次额外的模型调用）；备选直接截断（丢最旧的工具结果，零成本但丢信息）。
上下文窗口（真值）：deepseek-v4 = 384K；claude 4.x = 200K。
适用范围：预算机制对会话无感——当前 CLI 的一次 agent 运行（工具轮次累积）或未来的多轮会话都适用；/compact 指令本身不会发给模型。
待拍板：/compact 目前按“独立消息或行首指令”识别（read /compact 不触发）——避免“解释一下 /compact”这类正常问题误触发；若要子串匹配请说。
