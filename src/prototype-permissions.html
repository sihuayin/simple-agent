权限与安全：Deny / Allow / Ask + 受保护路径

要回答的问题：这套策略评估逻辑对不对——① Deny 短而准（rm -rf /、dd、curl|bash）；② Allow 覆盖日常安全操作（读文件、代码搜索、git 查看、npm 脚本）；③ Ask 兜底，write_file/edit_file 始终确认；④ 三轮按 action 类型遍历（deny → ask → allow），同类型先命中生效；⑤ 受保护路径是独立清单，即使 Allow 命中，路径匹配仍转 Ask。

要钉死的两个矛盾点： ① 兜底必须是被评估完三轮后的默认值，而不是数组里的一条规则——如果把 {tool:"bash", action:"ask"} 写成规则放进 ask 轮，它会遮蔽所有 allow 规则（npm run build 也会变 ask）。场景 7 演示这个陷阱。 ② bash 可以绕过受保护路径：cat .env 通过 bash 执行不会经过路径检查——除非 bash 的 allow 列表不放读取类命令（模型应改用带路径检查的 read_file）。场景 6 演示。
待拍板：ask 在非交互运行时的行为（本原型：阻止并回喂模型"需要人类确认"；TTY 下可升级为暂停询问）；规则来源（内置默认 vs 项目配置文件）。本特性同时关闭 tools 规格里推迟的 bash 沙箱项。
